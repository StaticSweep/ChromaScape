# Fedora remote Micro6 executor

## Implemented connection model

Windows ChromaScape remains at `http://192.168.1.6:8090`. Fedora is currently
`192.168.1.21`. Reserve both addresses in DHCP before deployment.

The Fedora agent registers and sends a heartbeat every 10 seconds to ChromaScape's
launcher-control integration at `POST /api/builder-goal/remote-launcher/heartbeat`.
ChromaScape merges this configured machine into the existing launcher machine list;
account discovery and existing Windows machines still use the separate launcher-control
service on 8084. No new session/command protocol is required in that external service.
This implementation supports one explicitly configured remote Fedora agent per
ChromaScape instance. Additional hosts would require a configuration collection.

The agent's bearer token, machine UUID, launcher origin, and executor origin are pinned
in Windows configuration. Heartbeats cannot select arbitrary HTTP destinations. A
machine is offline after 35 seconds without a compatible authenticated heartbeat.
Only contract 2 with `builder-goal-launch-v2` is accepted. Local Windows launch routing
continues to use the existing PowerShell adapter.

The agent owns one executor slot. It runs `:client:prepareBuilderGoal` followed by
`:client:runBuilderGoal` via the Linux contract-v2 adapter and fixed Gradle arguments.
It never accepts shell commands, workspace paths, arbitrary environment variables, or
extra client options. Launch IDs are UUIDs and persisted with an authenticated payload
fingerprint; replaying an ID cannot create another process. Force relaunch stops only
a previous command for the same account. A different account requires stopping the
occupied slot explicitly. Relaunch always uses a new command ID.

Readiness requires a fresh executor heartbeat with the selected machine UUID, canonical
actual and requested account hash, requested and current world, new launch attempt ID,
and dispatch-ready lifecycle. The advertised executor URL must match configuration.
Source changes add `machine_uuid` to Micro6's heartbeat. The machine/agent metadata and
command ID are retained in run preparation metadata. A lost agent, exited process, or
readiness timeout produces `REMOTE_LAUNCH_RECOVERABLE`; publishing stays blocked.
Existing executor monitoring detects executor loss after dispatch. The systemd unit
owns the agent and descendants, so stopping/restarting it also stops managed clients.

## Deployment prerequisites

Both repository branches `codex/fedora-remote-executor` must be deployed together.
Changes were created from each repository's committed HEAD; unrelated working-copy
changes were deliberately excluded. Review any local Linux build fixes separately.
Micro6 also needs its existing sibling capture-contract checkout and Gradle dependencies.

Use Python 3.9+ and Java 17+ on Fedora. Micro6 is a GUI client: run the user service as
the desktop user and import that user's `DISPLAY`, `XAUTHORITY`, and applicable session
environment. Boot registration works without a desktop; launching a visible client
requires a usable graphical session. A `/run/media/...` workspace must be mounted at
boot, before a remote launch. Prefer a persistent mount for unattended operation.

## Configure Windows

Put these in ChromaScape's ignored `.env.local`:

```dotenv
BUILDER_GOAL_REMOTE_MACHINE_UUID=<Fedora stable UUID>
BUILDER_GOAL_REMOTE_ENDPOINT=http://192.168.1.21:8101
BUILDER_GOAL_REMOTE_EXECUTOR_URL=http://192.168.1.21:8098
BUILDER_GOAL_REMOTE_TOKEN=<random secret of at least 32 characters>
BUILDER_GOAL_REMOTE_TIMEOUT_SECONDS=1800
```

Use a random token generated by a password manager or `openssl rand -hex 32`.
Do not put real tokens in Git. Restart Windows ChromaScape using the existing
`docs/CHROMASCAPE_RESTART_RUNBOOK.md` only when deployment is authorized.

## Configure Fedora

In Micro6, copy `scripts/remote-launcher/micro6-agent.env.example` to
`~/.config/micro6-agent.env`, restrict it to mode 600, and fill the workspace, script,
state directory, UUID, token, and advertised addresses. Use the same UUID and token as
Windows. Reuse an existing stable launcher UUID if Fedora already has one. Otherwise,
a UUID can be deterministically derived from `/etc/machine-id` using Python
`uuid.uuid5(uuid.NAMESPACE_OID, "micro6:" + machine_id.strip())`; the agent uses this
algorithm when no UUID is configured and persists the result in its state directory.
Never copy that state directory to another machine. Preserve it during upgrades.

The agent creates a per-launch `executor.env` containing the required remote executor
settings so a checkout's old `.env` cannot redirect heartbeats to localhost. Additional
Micro6 integration credentials must be supplied in the user service's environment.

When service startup is authorized, install the user unit:

```bash
mkdir -p ~/.config/systemd/user
cp scripts/remote-launcher/micro6-agent.service ~/.config/systemd/user/
chmod 600 ~/.config/micro6-agent.env
systemctl --user daemon-reload
systemctl --user import-environment DISPLAY XAUTHORITY
systemctl --user enable --now micro6-agent.service
loginctl enable-linger "$USER"
```

Enable lingering with appropriate system permissions. Check
`journalctl --user -u micro6-agent.service`. The agent retries failed heartbeats without
logging credentials. Per-launch status and logs live under
`~/.local/state/micro6-agent/<command UUID>/`. Protect these logs as account data.
Status files survive service restarts; unfinished commands become `interrupted` and
are never silently restarted. Explicitly relaunch from Windows with a new command ID.

## Network rules

Allow Fedora → Windows TCP 8090. Scope the Windows inbound rule to `192.168.1.21`.
Allow Windows → Fedora TCP 8101 (agent) and TCP 8098 (executor dispatch), scoped to
`192.168.1.6`. With firewalld, apply to the actual LAN interface's zone, for example:

```bash
sudo firewall-cmd --permanent --zone=<LAN-zone> --add-rich-rule='rule family="ipv4" source address="192.168.1.6/32" port port="8101" protocol="tcp" accept'
sudo firewall-cmd --permanent --zone=<LAN-zone> --add-rich-rule='rule family="ipv4" source address="192.168.1.6/32" port port="8098" protocol="tcp" accept'
sudo firewall-cmd --reload
```

Check for pre-existing broad port rules; rich rules do not remove them. The agent also
checks the caller's source address and bearer token. Plain HTTP is scoped to this trusted
LAN; use a TLS reverse proxy and HTTPS configuration if traffic must cross untrusted
networks. Do not expose the executor or agent to the internet.

## Agent API

Every request requires `Authorization: Bearer <token>` from the configured Windows IP.
`GET /v1/status` reports identity/capability. `POST /v1/launches` accepts the contract
payload assembled by ChromaScape, including `command_id`, `machine_uuid`, `account_hash`,
`world`, `force`, and `clientArgs`. `GET /v1/launches/<UUID>` returns status/log path.
`POST /v1/launches/<UUID>/stop` with `{}` requests process-tree termination; poll status
until `stopped`. The normal Builder Goal task Stop stops the task through the executor;
it does not imply stopping the whole client after a successful launch.

## Verification checklist (not yet executed)

1. Run ChromaScape's launcher/preparation/registry regression tests and Micro6's agent
   validation tests. Compile both projects explicitly before deployment.
2. Verify Fedora appears online only after its authenticated heartbeat; bad token,
   wrong UUID, wrong endpoint, and missing capability must be rejected.
3. Launch DogaAGI/world 360 from Windows. Confirm the process and logs are on Fedora;
   Windows must never invoke local process cleanup for this remote request.
4. Repeat the same command ID: it must not start another client. Mismatched payloads
   must fail. A stopped old command must remain stopped after an agent restart.
5. Confirm wrong machine/account/world/attempt and held lifecycle cannot unlock publish.
6. Publish a harmless task; confirm dispatch to Fedora, then stop the task.
7. Stop the agent and confirm process cleanup, offline status, and recoverable launch
   behavior. Restore the service and relaunch on the same UUID.
8. Reboot Fedora when authorized; confirm the mount, user service, stable identity,
   heartbeat registration, and availability of the desktop environment.
