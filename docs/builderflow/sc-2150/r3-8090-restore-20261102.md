# SC-2150 R3 — restore 8090 on the packaged candidate

Date: 2026-11-02. Follow-through for [R3 of the remaining plan](remaining-plan-20261102.md).

## Diagnosis

- Port 8090 had no listener; `http://127.0.0.1:8090/mouse/video` returned no connection.
- The configured Fedora runtime (`CHROMASCAPE_FEDORA_RUNTIME_PROJECT_DIR` in `.env.local`)
  pointed at `ChromaScape-sc663-runtime`, whose HEAD is the SC-663 review merge and which has no
  `mouse-video` classes. That checkout could not serve the SC-2150 feature.
- The review instance on 18191 was healthy and uses `ChromaScape-main-runtime`; it was left
  running and unchanged.

## What was run

1. Built and tested the scoped candidate in a clean worktree from `origin/main`
   (`codex/sc-2150-assisted-review-r1`).
2. Backed up the `chromascape` database on `127.0.0.1:5433` as
   `chromascape_backup_sc2150r1_20261102` (17 MB, `CREATE DATABASE ... TEMPLATE`).
3. Started the candidate with the `fedora-development` profile, loopback-only endpoints and the
   assisted mouse-video settings. Flyway validated all 81 migrations; schema version 86 was
   already current and no migration was applied.
4. Verified endpoints and the capability report, then stopped and restarted the process and
   verified them again.

The canonical `scripts/start-fedora-dev.sh` is not present on `origin/main`; it exists only in
the preserved development branch. This run used an equivalent direct `bootRun` with the same
profile, endpoints and environment loading, and left `.env.local` unchanged. The runtime is the
candidate worktree, not a separate durable clone; a durable runtime checkout remains a follow-up
before the worktree is removed.

### Correction (2026-11-03, later the same day): the deployed process must be the runtime checkout

While preparing the R7 receipts it became visible that 8090 was being relaunched by an external tmux
watchdog (`/tmp/start-8090-candidate.sh`, started 2026-11-02) that pinned the **candidate worktree**,
the ephemeral `build/sc2150-assisted/clip-arrow.png` template and the candidate media directory, and
did not set the local-operator flag. Every stop was followed by a fresh candidate-classpath process,
which is why the first write-smoke attempt on 8090 answered `401`.

Resolution: that entry point was backed up
(`/tmp/start-8090-candidate.sh.bak-20261103`) and rewritten to delegate to the canonical
`ChromaScape-runtime-sc2150/scripts/start-fedora-dev.sh` with a clean environment, so there is one
