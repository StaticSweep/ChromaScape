### Architecture and API

The existing `patch_loop_event` table carries an append-only event vocabulary; no schema migration is added. The event recorder stamps task/script/session identity, includes failure code/reason, sorts reads by timestamp/id, and guards the entire REQUIRES_NEW transaction including commit failures. Locked state mutations schedule events after commit so rolled-back state cannot publish ghost events and recording cannot roll back controls. Stop intent precedes pre-publish cancellation in the timeline. Risk inspection now runs before terminal/STOPPING returns so a risk reported together with failure or cancellation is retained.

`GET /api/debug/builder-goals/runs/{iterationId}/events` returns an event array, 404 for a missing run, and 500 for unavailable reads, using existing debugger API conventions. The browser treats missing runs, malformed JSON, malformed event lists and HTTP errors as explicit errors. Only a valid empty array renders no events. Request generations prevent stale results/errors from overwriting a newly selected run or a newer request for the same run.

### UI and update design

Each run card offers Timeline. The panel displays chronological lifecycle/risk events with escaped identity and reason details, a loading state, and an actionable error alert. A selected panel polls every three seconds after each completed request independently of the run tracker, retries failed final/history reads, and stops on close. The tracked active run continues its two-second status polling; the run-list refresh is reduced from ten to five seconds. Timings are nominal network-healthy cadences, not a certification of end-to-end latency under arbitrary network delays or browser timer throttling. Bundle version 46 is consistent across JS, template, and existing bundle tests.

### Given / When / Then acceptance criteria

1. Given an active run, when executor status changes, then Start/Complete/Fail/Pause/Resume/Stop events render in chronological order and status polling continues after RUNNING.
2. Given risk data in an active, terminal or STOPPING status response, when that observation is persisted, then the reported risk remains in the timeline.
3. Given a failed run, when its timeline is loaded, then failure code/reason and owning task/script context are present and escaped.
4. Given a selected timeline without an active tracker, when its API recovers or new events appear, then polling continues at the three-second cadence until the panel closes.
5. Given missing/invalid/unavailable API data, when loading completes, then the panel reports a clear error instead of pretending the timeline is empty; a status API failure immediately marks the status panel degraded while retrying.
6. Given overlapping requests or a changed selected run, when an older response/error arrives, then it cannot overwrite current events.
7. Given a run-state transaction rollback or event-storage commit error, when recording is attempted, then no rolled-back state event is published and event failure cannot break run control.
8. Given current main integration, when compilation and relevant regressions run, then current source binding, packet capture, paused/stop reconciliation and recovery behavior remain intact.
