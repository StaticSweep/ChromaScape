## Architectural decisions

1. Add packets to the existing ACK-backed `TICK_BATCH`. Do not create a parallel Micro6-to-ChromaScape packet WebSocket.
2. Bump newly produced batches to `schemaVersion: 3`. ChromaScape must continue reading schema-v2 batches/recordings with packets absent.
3. Use a new, versioned RSProx local stream `rsprox-packet-stream/v1`: 4-byte big-endian length followed by UTF-8 JSON. Do not expose RSProx protocol/JVM classes across the process boundary.
4. Preserve the existing Kryo tunnel and sync events unchanged for legacy consumers. Select the v1 stream through a distinct connection filename/prefix or an explicit negotiated mode; never reinterpret legacy bytes.
5. Produce envelopes after decryption and current redaction. Raw bytes are disabled by default.
6. Bind packet observations only while a ChromaScape debug session is active. Clear stale pre-session data on session start, stop, or authoritative rebind.
7. Persist packets in a dedicated table, not inside the high-volume `tick_snapshots` JSON.
8. Include `packets` in the canonical batch checksum after all size-limit degradation is complete.
9. Do not forward packet bodies to the Go backend by default. Strip `packets` from that optional forwarding path unless a separately reviewed contract enables them.
10. Packet capture must never block Netty, RuneLite's game thread, the WebSocket sender, the ChromaScape transaction indefinitely, or browser rendering.

## Wire contract

### RSProx to Micro6 envelope

Use this logical shape. Names are normative; Java/Kotlin types may differ.

```json
{
  "schema": "rsprox-packet/v1",
  "sourceSessionId": "proxy-session-uuid",
  "sequence": 4812,
  "capturedAt": "2026-09-04T18:12:34.567Z",
  "captureDeltaMillis": 4,
  "direction": "SERVER_TO_CLIENT",
  "opcode": 81,
  "protocolName": "NPC_INFO_LARGE",
  "encodedSize": 137,
  "decodedType": "NpcInfo",
  "decoded": {},
  "sanitizedPayloadBase64": null,
  "decodeStatus": "DECODED",
  "decodeError": null,
  "synthetic": false
}
```

Rules:

- `sequence` is monotonic within `sourceSessionId`.
- Directions are exactly `CLIENT_TO_SERVER` and `SERVER_TO_CLIENT`.
- `decodeStatus`: `DECODED`, `UNKNOWN_PROTOCOL`, `DECODE_ERROR`, or `GAP`.
- `synthetic=true` is used only for gap/stream lifecycle observations.
- `decoded` must be a bounded JSON object/array/scalar produced by an explicit safe serializer; never arbitrary Java/Kotlin serialization.
- `decodeError` is a bounded, sanitized category/message and must not contain stack traces, raw credentials, or unredacted packet bytes.
- `sanitizedPayloadBase64` is nullable and disabled by default. If enabled, cap per-packet and per-batch bytes before enqueueing.
- Add an assigned `tick` when Micro6 incorporates the envelope into a batch. ChromaScape treats that per-packet tick as authoritative within the active session.
- Preserve RSProx's actual protocol opcode. If a synthetic `SERVER_TICK_END` has no wire opcode, mark `synthetic=true` rather than pretending it was on the wire.

### Tick-batch extension

```json
{
  "type": "TICK_BATCH",
  "schemaVersion": 3,
  "batchId": "uuid",
  "sessionId": "chromascape-session-id",
  "tick": 12004,
  "packets": [],
  "transport": {
    "droppedPacketCount": 0,
    "firstDroppedPacketSequence": null,
    "lastDroppedPacketSequence": null,
    "omittedPacketCount": 0,
    "omittedPacketPayloadBytes": 0,
    "packetSourceStatus": "CONNECTED"
  },
  "payloadChecksum": "sha256"
}
```

Packets can span earlier observed ticks when `tickBatchInterval > 1`; each envelope therefore carries its assigned `tick`. The browser must group by the envelope tick, not blindly by the enclosing batch tick. Sequence remains the cross-tick ordering authority.

## Failure and lifecycle behavior

- RSProx absent: Micro6 starts normally; packet source shows `UNAVAILABLE`; ordinary tick batches continue.
- RSProx disconnect: retain already sealed packets, reconnect with bounded exponential backoff, emit source/gap diagnostics.
- Malformed envelope: drop only that frame, increment malformed count, close/reconnect after a threshold; never allocate its claimed oversized length.
- Buffer overflow: coalesce into a visible sequence gap; never silently discard.
- ChromaScape payload too large: Micro6 applies deterministic packet degradation before checksum/send.
- ChromaScape transaction failure: no ACK; existing batch retry retains identical packet sequences.
- Duplicate retry: idempotent rows and identical ACK.
- Session stop: do not attach packets from the old ChromaScape session to a new session.
- UI reconnect: live feed resumes; persisted replay remains authoritative for earlier packets.
- Go forwarding: packets remain excluded unless separately enabled and versioned.

## Given/When/Then acceptance criteria

1. **Live visibility**
   - Given RSProx launches the packet-enabled Micro6 overlay and a ChromaScape debug session is active,
   - When incoming and outgoing game packets are captured,
   - Then `/debugger` shows them under the correct session and assigned tick.

2. **Packet fidelity**
   - Given packets in both directions,
   - When they reach the debugger,
   - Then direction, session-scoped sequence, capture time/delta, opcode, protocol name, encoded size, decoded type/status, and synthetic marker preserve source order and meaning.

3. **Durability**
   - Given a schema-v3 batch with packets,
   - When ChromaScape sends `TICK_BATCH_ACK status=PERSISTED`,
   - Then the packet rows and batch receipt committed in the same transaction.

4. **Retry idempotency**
   - Given an ACK is lost after commit,
   - When Micro6 retries the identical batch,
   - Then ChromaScape returns the durable ACK without inserting duplicate packet rows.

5. **Replay**
   - Given a recorded session is closed and ChromaScape restarts,
   - When the session is opened in replay mode,
   - Then the same packet rows load from the paginated replay API.

6. **Redaction**
   - Given bank-pin keyboard input, private messages, secure URLs, UID data, or site settings,
   - When packet observation is enabled,
   - Then no unredacted secret appears in the RSProx envelope, Micro6 logs/batches, ChromaScape DB/API/logs, browser DOM, screenshots, or evidence.

7. **Compatibility**
   - Given an old Kryo tunnel consumer or schema-v2 recording/client,
   - When the new implementation is deployed,
   - Then the legacy consumer/recording remains usable and packets default to absent/empty.

8. **Backpressure**
   - Given a burst, slow consumer, oversized batch, or disconnected service,
   - When limits are exceeded,
   - Then bounded queues protect all threads and the debugger displays exact drop/omission/gap diagnostics.

9. **Unavailable source**
   - Given Micro6 is not launched through RSProx,
   - When Debug Recorder streams ticks,
   - Then tick streaming continues and the packet UI says source unavailable without hanging startup.

10. **UI safety**
    - Given large decoded fields or hostile text values,
    - When rows render,
    - Then content is escaped, details are lazy/bounded, and the page remains responsive.

## SC-1618 v2 current execution addendum

This addendum supersedes any v1 identity assumptions in the historical plan while preserving its scope and compatibility requirements.

### Current v2 identity and loss contract

RSProx emits `rsprox-packet/v2` observations. `sequence` is a per-`sourceSessionId` delivery/observation identity allocated once when an observation enters delivery order; `packetSequence` is the original capture identity for real packets and is null for GAP observations. Real observations and GAPs consume the same source-scoped observation allocator. Requeue, retry, reconnect, and repeated delivery preserve the assigned observation identity. GAPs retain their source ID, represented count, and first/last capture-sequence bounds; a failed GAP returns those represented losses to pending diagnostics rather than discarding them. v1 remains explicit: its sequence retains legacy capture semantics and is never silently reinterpreted as v2.

### Current delivery ownership contract

Micro6 accepts v1 and v2 explicitly, keeps per-source duplicate/order state, and preserves both identities through tick assignment, truncation, checksums, retry serialization, and durable acknowledgement. Diagnostics are detached into immutable batch-owned snapshots; losses after detachment belong to the next batch. Pre-transport rejection restores a snapshot once, accepted batches remain owned by WebSocket retry, and terminal failure does not repeatedly requeue invalid data. Old-session callbacks cannot mutate new-session evidence.

### Current persistence and replay contract

ChromaScape validates v1/v2 packet fields, persists observations with the V43/V44 compatibility migrations, enforces source/session-aware identity uniqueness, treats identical retries as idempotent, and rejects changed content under an existing identity permanently. Packet rows and batch receipts commit together before ACK; committed packets are published after commit. Replay ordering and cursors use the same tick/source/observation ordering, and browser recovery subtracts only the interval successfully loaded. V39 is not edited.
